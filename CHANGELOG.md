- **Fix: no more false "server is powered off" alert on an unexpected power state.** The collector translated `OperPowerState` into `power_state`: `on` → 1, any other value → 0. An unexpected value was therefore shown as "Off" and raised "Intersight: server is powered off". Yet the SDK sets no list of values: "The actual power state of the server." (SDK CiscoDevNet/intersight-python, `compute_physical_summary_all_of.py`). Only `on` and `off` were observed on an appliance during design.
  - **Collector**: `on` → 1, `off` → 0, any other non-empty value → 2, case-insensitive. If `OperPowerState` is absent or empty, `power_state` is still not sent.
  - **Template**: the value map "Power state" gains `2` → `Other` (it is defined in the three device templates; only the server template has the item). The trigger "Intersight: server is powered off" (`=0`, AVERAGE, manual close) does not change.
  - **New trigger** WARNING "Intersight: unexpected power state reported" (`=2`), without manual close: the problem closes by itself when the value becomes `on` or `off` again. It asks to check the power state of the server in Intersight. The two triggers are mutually exclusive (0 or 2): no dependency between them.
  - Same item key (`intersight.power.state`), same type, same meaning for 0 and 1: the history is kept and there is nothing to tick on re-import. When a template is imported, "Update existing" and "Create new" are ticked by default for value maps and triggers (Zabbix 7.0 code, `CControllerPopupImport.php`). Test: `tests/power_state.test.js`.
- **Fix: stable paging of the Intersight lists (sorted by `Moid`).** The lists (servers, chassis, FIs, alarms) are read in pages of 1,000 (`$top`, `$skip`), until now without a sort order. The Cisco doc states: "You can specify $orderby to sort the results such that paginated results are returned in a predictable order" (Cisco Intersight API Docs, "Query Language", section "$top and $skip Query Options: Pagination"), and gives no default order. If the order changed between two pages, an object could therefore be skipped or read twice.
  - **Collector**: each page is requested with `$orderby=Moid`. The `Moid` is unique (SDK CiscoDevNet/intersight-python, `mo_base_mo.py`: "The unique identifier of this Managed Object instance"), which gives a total order. A field such as `CreationTime`, taken as an example by the doc, can have ties. Verified on an appliance during design: `$orderby=Moid` is accepted with `$top`, `$skip`, `$filter` and `$select` (`compute/PhysicalSummaries`, `cond/Alarms`), and the results come back sorted by `Moid`.
  - **Truncated list reported**: the collector reads at most 20,000 objects per list (`MAX_ITEMS_PER_LIST`, unchanged). Before, a longer list was cut without anything being reported. Now, if the last page read is full, "API: last errors" shows `<API path>: list truncated at 20000 objects`. The objects read are kept and remain monitored.
  - **Consequence of a truncated list**: the objects beyond the limit (the last ones in `Moid` order) are not discovered. The hosts that already existed are therefore treated as lost resources (disabled after `{$INTERSIGHT.HOST.LOST.DISABLE}`, deleted after `{$INTERSIGHT.HOST.LOST.DELETE}`), and the alarms beyond the limit are not reflected. A list of exactly 20,000 objects is reported too: without an extra request, it cannot be told apart from a longer list.
  - No item key change: nothing to tick on re-import. Test: `tests/inventory_paging.test.js`.
- **`is_blade` read from `SourceObjectType`, with a fallback.** `is_blade` (1 blade, 0 rack) is only used by the nested mode of Zabbix 7.4 (`flat_servers=0`), to remove the blades from the "Servers" discovery. It was inferred: 1 if the server had a chassis (`EquipmentChassis` or `ChassisId`) or a `UCSB-*` / `UCSX-*` model. It now comes from the type of the source object, provided by `compute/PhysicalSummaries`: `compute.Blade` → 1, `compute.RackUnit` → 0 (SDK CiscoDevNet/intersight-python, `compute_physical_summary_all_of.py`: "This feild will either be RackUnit or Blade"). Only these two values were observed on an appliance during design.
  - **Fallback**: if `SourceObjectType` is absent or has another value (another installation may not return it), the old rule applies.
  - The Zabbix 7.0 mode (default) is not affected: all the servers are discovered in it. Test: `tests/blade_chassis_matching.test.js`.
- **Fix: telemetry attached by `host.id` (the `Moid` of the device), with a fallback on the name.** Before, telemetry was attached by class (`host.type`) and name (`host.name`). Yet Cisco states that "the host name is not guaranteed to be unique and may change over time", whereas `host.id` is "a globally unique host ID", the API path of the resource (Cisco DevNet doc, "Host Power and Status"). Two devices of the same class with the same name therefore received the same mixed telemetry (power, temperatures, PSUs, ports). No duplicate was observed on the appliance used during design: this is a protection for other installations.
  - **Collector**: all the requests are also grouped by `host.id` (attribute documented for the 13 instruments of the catalog). Each row is attached to the device whose `Moid` is the last segment of `host.id` (form `/api/v1/<space>/<class>/<id>`). Verified on an appliance during design, for `hw.host` and `hw.power_supply`: this segment is the `Moid` of the blades, racks, chassis and FIs, and each `host.id` corresponds to a single name and a single type. Not verified for the other instruments (`hw.network`, `hw.temperature`…).
  - **Fallback**: another installation may not return `host.id`. A row without `host.id` (absent or empty) is attached by class and name, or by name alone if `host.type` is unknown, from the inventory read just before. A device thus receives all its rows, even if one instrument returns `host.id` and another does not.
  - **Limit of the fallback**: if a name is carried by several devices (of the same class, or of any class when `host.type` is unknown), its rows without `host.id` are ignored. These homonyms do not receive this telemetry, rather than mixed values. A row whose `host.id` matches no device of the inventory is attributed to no device.
  - **Robustness**: the table indexed by `Moid` has no prototype (`Object.create(null)`). A last segment of `host.id` such as `__proto__` or `constructor`, read from the HTTP response, can therefore no longer designate an inherited property, nor write the telemetry into `Object.prototype`, from which all objects would have inherited it (Copilot review of PR #22).
  - No item key change: nothing to tick on re-import. Test: `tests/telemetry_match_by_host_id.test.js`.
- **Fix: a failed telemetry request no longer disables the PSUs and the ports.** When the `hw.power_supply` or `hw.network` request failed, the collector sent `psus = []` or `ports = []` for each device, and the rules "PSU discovery" and "Network port discovery" replaced a missing list with `[]` anyway (`CUSTOM_VALUE`). All the PSUs or all the ports of all the devices were then declared lost: disabled after `{$INTERSIGHT.LLD.LOST.DISABLE}` (`1h`), deleted after `{$INTERSIGHT.LLD.LOST.DELETE}` (`7d`). Same defect as the one fixed for the inventory lists (below).
  - **Collector**: if the `hw.power_supply` request failed, `psus` is no longer sent; if the `hw.network` request failed, `ports` is no longer sent. The error appears in "API: last errors". A successful request without a row for a given device still gives `[]` (for example, a blade has no PSU).
  - **Template**: on the rules "PSU discovery" and "Network port discovery" of the three device templates, a missing list makes the rule discard the value (`DISCARD_VALUE`) instead of declaring the components lost. The delays `{$INTERSIGHT.LLD.LOST.*}` remain a second protection.
  - Nothing to tick on re-import. Test: `tests/telemetry_failure_components.test.js`.
- **Monitoring of the size of the JSON pushed to `intersight.raw`.** This Text item is stored in the database (1 h of history), and Zabbix truncates a Text value before storing it: 65,536 bytes on MySQL, 65,536 characters on PostgreSQL (Zabbix 7.0 doc, "Creating an item", "Text data limits"). `history_text.value` is of type `t_text`, i.e. `text` on MySQL (`create/src/schema.tmpl` and `create/bin/gen_schema.pl` of Zabbix 7.0), which holds at most 65,535 bytes (MySQL 8.0 doc, "String Data Type Syntax"). No storage change for now.
  - **Collector**: new fields `api.max_push_bytes` (size in UTF-8 bytes of the largest pushed JSON) and `api.max_push_moid` (Moid of its device). Absent if push is disabled or if there is no device; present even if the `history.push` request fails.
  - **Parent template**: items "API: largest pushed value" (`intersight.api.push.max.bytes`, unit `B`) and "API: device of the largest pushed value" (`intersight.api.push.max.moid`), which discard a missing value (`DISCARD_VALUE`). WARNING trigger "Intersight: pushed value larger than {$INTERSIGHT.RAW.SIZE.WARN} bytes", with the new macro `{$INTERSIGHT.RAW.SIZE.WARN}` = `50000`. A size in bytes is never less than the number of characters: the same threshold applies to MySQL and PostgreSQL. When the measurements stop (push disabled or no device), the missing value is discarded and the problem closes after 20 minutes without a measurement (`nodata`, Zabbix 7.0 doc, "History functions").
  - **Unit `B`** added to the allowed units. Zabbix shows it in base 2: 1,024 B → "1 KB", 1,536 B → "1.5 KB" (Zabbix 7.0 doc, "Unit symbols", "Item value suffixes").
  - New items: nothing to tick on re-import. Test: `tests/push_size.test.js`.
- **Fix: a failed inventory read disabled all the hosts of the type.** When reading the servers, the chassis or the FIs failed, the collector sent an empty list, and the rules "Servers discovery", "Chassis discovery", "Fabric Interconnects discovery" and "Models discovery" replaced a missing list with `[]` anyway. These rules only set the deletion (`lifetime: 7d`): on import into Zabbix 7.0, disabling then takes the default value "immediately" (`DISABLE_IMMEDIATELY`, Zabbix 7.0 code, `C70XmlValidator.php`), and it "affects lost hosts, items and triggers" (Zabbix 7.0 doc, "Low-level discovery"). All the hosts of the type were therefore disabled until the next cycle.
  - **Collector**: a list whose read failed is no longer sent (`servers`, `chassis` or `fis`), and neither is `models`, since it would be incomplete. The devices that were read are still pushed, and the error appears in "API: last errors". A really empty list (no device of this type in Intersight) is still sent as `[]`.
  - **Alarm totals**: when the `cond/Alarms` request failed, the `alarms` totals (critical, warning, info) are no longer sent as zero, but not at all. The items `intersight.alarms.total.*` already discard a missing value (`DISCARD_VALUE`): they keep their last value.
  - **Counters**: the count of a type whose read failed (`counts.servers`, `counts.chassis` or `counts.fi`) is no longer sent. The items "Count: …" already discard a missing value (`DISCARD_VALUE`): they keep their last value instead of dropping to 0.
  - **Blades (Zabbix 7.4 nested mode)**: if reading the servers failed, the chassis no longer have a `blades` list, instead of an empty list that would have declared all the blades lost. In `docs/UPGRADE_7.4_FR.md`, the rule "Blades discovery" created by hand must now discard a missing value ("Custom on fail" → Discard value).
  - **Blade delays (Zabbix 7.4 nested mode)**: the template "Cisco Intersight Chassis by push" also defines `{$INTERSIGHT.HOST.LOST.DISABLE}` (`1h`) and `{$INTERSIGHT.HOST.LOST.DELETE}` (`7d`). The rule "Blades discovery" runs on the chassis hosts, which do not inherit the macros of the parent template: the same values must be kept on both templates. `docs/UPGRADE_7.4_FR.md` applies them to this rule ("Delete lost resources" and "Disable lost resources" = After, one macro per field), and explains what happens when reading the servers or the chassis fails. These steps have never been applied on a real Zabbix 7.4.
  - **Template**: on these four rules, a missing list makes the rule discard the value (`DISCARD_VALUE`) instead of declaring the hosts lost.
  - **Second protection**: disabling after `{$INTERSIGHT.HOST.LOST.DISABLE}` (`1h` by default), deletion after `{$INTERSIGHT.HOST.LOST.DELETE}` (`7d` by default, as before). **Deletion must stay longer than disabling** (Zabbix 7.0 doc, "Low-level discovery"). Each field contains only one macro: it is the value of the macros that is changed, not the fields.
  - Not verified: the Zabbix doc does not say what happens to the open problems of a disabled host.
- **Fix: PSUs and ports disabled at the first cycle without telemetry.** The rules "PSU discovery" and "Network port discovery" only set the deletion (`lifetime: 7d`). On import into Zabbix 7.0, disabling then takes the default value "immediately" (`DISABLE_IMMEDIATELY`, Zabbix 7.0 code, `C70XmlValidator.php`). Yet the collector sends empty `psus` and `ports` lists when a device has no telemetry during a cycle: all its PSUs and all its ports were therefore disabled, then enabled again at the next cycle (Zabbix 7.0 doc, "Low-level discovery").
  - Now, on the three device templates: disabling after `{$INTERSIGHT.LLD.LOST.DISABLE}` (`1h` by default), deletion after `{$INTERSIGHT.LLD.LOST.DELETE}` (`7d` by default, as before).
  - **Deletion must stay longer than disabling** (Zabbix 7.0 doc, "Low-level discovery"). Each field contains only one macro: it is the value of the macros that is changed, not the fields.
  - The alarm rule keeps its own macros (`{$INTERSIGHT.ALARM.LOST.*}`).
- **Intersight alarms → Zabbix problems**: each Intersight alarm becomes a problem on the host of its device (server, chassis or FI whose `Moid` is equal to the `AncestorMoId` of the alarm). Alarms without a known device (platform objects, unknown ancestor) go to the parent host. One-way mirror: nothing is written to Intersight. Details in the README, section "Intersight alarms".
  - A single `cond/Alarms` request per cycle (non-Cleared alarms + recent Cleared alarms) replaces the former request for unacknowledged alarms. The existing alarm counters do not change. `AcknowledgeBy` (name of a person) is never read.
  - New discovery rule "Intersight alarms" on the four templates: items `intersight.alarm.severity[…]`, `.ack[…]`, `.suppressed[…]` (1 h heartbeat), three mutually exclusive triggers, tags `component: alarm` and `alarm-code`.
  - Severities: Critical → High (not Disaster), Warning → Warning, Info → Information (prototype can be disabled), Cleared → problem closed. Alarms of severity `None` are not pushed.
  - Acknowledging or suppressing an alarm in Intersight **does not close** the problem: it stays open and the Intersight state is shown in its operational data. Only Cleared closes it.
  - New macros: `{$INTERSIGHT.ALARM.CLEARED.WINDOW}` = `1d`, `{$INTERSIGHT.ALARM.NODATA}` = `2h` (must stay greater than the 1 h heartbeat), `{$INTERSIGHT.ALARM.LOST.DISABLE}` = `1d`, `{$INTERSIGHT.ALARM.LOST.DELETE}` = `7d`. **Deletion must stay longer than disabling** (Zabbix 7.0 doc, "Low-level discovery").
  - To check after import: whether `{ITEM.LASTVALUE2}` and `{ITEM.LASTVALUE3}` show the raw value or the label of the value map.
- **Base units only**: values are stored in W, Wh, g and s instead of kWh, kg and ms, so that Grafana and external time-series databases receive the raw value. Zabbix only adds the K/M/G prefixes on display ("1.5 KWh").
  - 24 h energy in `Wh` (no more `/1000`). **Renamed key** `intersight.energy.kwh.24h` → `intersight.energy.24h`: new UUID, the history of the old item is lost on re-import.
  - Cost: `energy × {$INTERSIGHT.ENERGY.PRICE} / 1000` (the price stays per kWh). CO₂ in `g` (the intensity stays in gCO₂/kWh).
  - API durations in seconds (unit `s`): JSON fields `api.duration_s` and `api.sign_s` (instead of `duration_ms`, `sign_ms`), threshold of the trigger "collector close to its 120s timeout" at 90 s.
  - **Each item whose unit changes has a new key**, hence a new series: the old history (kWh, kg, ms) is never read again in the new unit, and the cost cannot read a total still in kWh. Renamed keys: `intersight.api.duration` → `intersight.api.run.time`, `intersight.api.sign` → `intersight.api.sign.time`, `intersight.total.energy[…]` → `intersight.total.energy.24h[…]`, `intersight.total.co2[…]` → `intersight.total.co2.24h[…]`, and likewise for `intersight.model.energy` / `intersight.model.co2`. The cost keeps its key (still in EUR).
  - **On re-import**, the option "Delete missing" must be ticked for items: otherwise the old items are not deleted and remain next to the new ones (Zabbix 7.0 doc, "Import rules"). Their history is then deleted; it can be exported beforehand if needed. The new totals stay empty until their first calculation (1 h interval).
- Fix: the `blades` list of each chassis stayed empty. On an appliance, the `RegisteredDevice` of a blade differs from that of its chassis, so the key `RegisteredDevice.Moid:ChassisId` never matched. A blade is now attached through the `EquipmentChassis` relationship of `compute.PhysicalSummary` (Intersight API schema, SDK CiscoDevNet/intersight-python); the old key is only used as a fallback. Only the nested mode of Zabbix 7.4 (`flat_servers=0`) was affected.
- Fix: the aggregated item "{#CLASS} {#MODEL}: devices reporting", renamed "{#CLASS} {#MODEL}: device count", counted the devices that had a power value (`intersight.power`). Intersight provides no power value for some devices (observed on chassis and servers; unknown cause; the other device types were not checked exhaustively): they were therefore not counted. The item now counts the devices that have an `intersight.model` value, which the collector always fills in (`unknown` if Intersight gives none). Same key and same unit: the history is kept, but the earlier values follow the old counting.
- New field `chassis_moid` on the servers (Moid of the chassis, empty for a rack); test `tests/blade_chassis_matching.test.js`.

## 7.0-6
- Import fix: `Invalid parameter "/N/params": value is too long`. Zabbix limits scripts to 65,535 characters, and the commented collector has 71,266. The template now embeds a comment-free copy (about 56,000 characters), generated automatically; `src/collector.js` remains the commented source.
- `tools/validate_template.py` checks the length of the scripts.
- `tests/embedded_script.test.js` runs the collector tests on the embedded copy, the one that Zabbix actually runs.
- **Rule: no inferred field name.** `docs/intersight_metrics.json` is the catalog extracted from the Intersight "Supported Metrics" pages (13 instruments, 146 metrics, 724 fields, through `tools/build_metrics_catalog.py`). `tests/documented_fields.test.js` fails on any field or dataSource that is not in the catalog.
- Each item is only created on the devices whose type is listed in the "Support information" of the metric (ECC: servers; CPU `system.cpu` and memory: FIs; temperature and fan margins: servers, chassis or FIs depending on the threshold).
- Network throughput per port (bits/s) and link speed, with the formula of the Grafana dashboards intersight-grafana: `sum(io_receive) / sum(io_receive_duration) × 8`. All the fields used are in the catalog; the formula, however, comes from these dashboards and not from the Cisco doc.
- Grouping by "dotted" attributes (`host.name`, `host.type`, `hw.network.port.role`) through `nested-field` virtual columns, as in these same dashboards.
- **Units checked**: Cisco documents the utilizations in `%`, but, on an appliance, the raw data are 0–1 ratios (0.1 = 10 %). A single macro, `{$INTERSIGHT.PERCENT.SCALE}` = 100, applies to all the utilizations (CPU, memory, PSU, network). Runtime checks (percentage > 100 %, CPU idle ≤ 1 on all the FIs) and a dedicated test are added.
- Zabbix units `!kWh`, `!kg`, `!EUR`, `!ms`, `!rpm`: no more absurd automatic prefixes ("1.5 KkWh").
- Port filter by role (`{$INTERSIGHT.PORT.ROLE.NOT_MATCHES}`): virtual interfaces and unconfigured ports ignored by default.
- Power of the IMM chassis: sum of the input power of the PSUs (`hw.power`) instead of their output power.
- Telemetry endpoint: `/api/v1/telemetry/TimeSeries`, the one documented by Cisco.
- Default configuration for the Advantage license (collection every minute): telemetry window of 10 minutes. With Essentials (collection every 10 minutes), `{$INTERSIGHT.WINDOW}` must be set to 30.
