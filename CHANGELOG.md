# Changelog

## Non publié
- **Correctif : plus de fausse alerte « server is powered off » sur un état d'alimentation inattendu.** Le collecteur traduisait `OperPowerState` en `power_state` : `on` → 1, toute autre valeur → 0. Une valeur inattendue s'affichait donc « Off » et déclenchait « Intersight: server is powered off ». Or le SDK ne fixe aucune liste de valeurs : « The actual power state of the server. » (SDK CiscoDevNet/intersight-python, `compute_physical_summary_all_of.py`). Seules `on` et `off` ont été observées sur l'appliance.
  - **Collecteur** : `on` → 1, `off` → 0, toute autre valeur non vide → 2, sans tenir compte de la casse. Si `OperPowerState` est absent ou vide, `power_state` n'est toujours pas envoyé.
  - **Template** : la table de valeurs « Power state » gagne `2` → `Other` (elle est définie dans les trois templates d'équipement ; seul le template serveur a l'item). Le trigger « Intersight: server is powered off » (`=0`, AVERAGE, fermeture manuelle) ne change pas.
  - **Nouveau trigger** WARNING « Intersight: unexpected power state reported » (`=2`), sans fermeture manuelle : le problème se ferme seul quand la valeur redevient `on` ou `off`. Il invite à vérifier l'état d'alimentation du serveur dans Intersight. Les deux triggers sont exclusifs (0 ou 2) : pas de dépendance entre eux.
  - Même clé d'item (`intersight.power.state`), même type, même sens pour 0 et 1 : l'historique est conservé et il n'y a rien à cocher à la réimportation. À l'import d'un template, « Update existing » et « Create new » sont cochés par défaut pour les tables de valeurs et les triggers (code de Zabbix 7.0, `CControllerPopupImport.php`). Test : `tests/power_state.test.js`.
- **Correctif : pagination stable des listes Intersight (tri par `Moid`).** Les listes (serveurs, châssis, FI, alarmes) sont lues par pages de 1 000 (`$top`, `$skip`), jusqu'ici sans ordre de tri. La doc Cisco indique : « You can specify $orderby to sort the results such that paginated results are returned in a predictable order » (Cisco Intersight API Docs, « Query Language », section « $top and $skip Query Options: Pagination »), et ne donne aucun ordre par défaut. Si l'ordre changeait entre deux pages, un objet pouvait donc être sauté ou lu deux fois.
  - **Collecteur** : chaque page est demandée avec `$orderby=Moid`. Le `Moid` est unique (SDK CiscoDevNet/intersight-python, `mo_base_mo.py` : « The unique identifier of this Managed Object instance »), ce qui donne un ordre total. Un champ comme `CreationTime`, pris en exemple par la doc, peut avoir des égalités. Vérifié sur l'appliance : `$orderby=Moid` est accepté avec `$top`, `$skip`, `$filter` et `$select` (`compute/PhysicalSummaries`, `cond/Alarms`), et les résultats reviennent triés par `Moid`.
  - **Liste coupée signalée** : le collecteur lit au plus 20 000 objets par liste (`MAX_ITEMS_PER_LIST`, inchangé). Avant, une liste plus longue était coupée sans rien signaler. Désormais, si la dernière page lue est pleine, « API: last errors » affiche `<chemin de l'API>: list truncated at 20000 objects`. Les objets lus sont conservés et restent supervisés.
  - **Conséquence d'une liste coupée** : les objets au-delà de la limite (les derniers dans l'ordre des `Moid`) ne sont pas découverts. Les hôtes qui existaient déjà sont donc traités comme ressources perdues (désactivés après `{$INTERSIGHT.HOST.LOST.DISABLE}`, supprimés après `{$INTERSIGHT.HOST.LOST.DELETE}`), et les alarmes au-delà de la limite ne sont pas reflétées. Une liste d'exactement 20 000 objets est aussi signalée : sans requête de plus, on ne peut pas la distinguer d'une liste plus longue.
  - Aucun changement de clé d'item : rien à cocher à la réimportation. Test : `tests/inventory_paging.test.js`.
- **`is_blade` lu dans `SourceObjectType`, avec repli.** `is_blade` (1 lame, 0 rack) ne sert qu'au mode imbriqué de Zabbix 7.4 (`flat_servers=0`), pour retirer les lames de la découverte « Servers ». Il était déduit : 1 si le serveur avait un châssis (`EquipmentChassis` ou `ChassisId`) ou un modèle `UCSB-*` / `UCSX-*`. Il vient désormais du type de l'objet source, fourni par `compute/PhysicalSummaries` : `compute.Blade` → 1, `compute.RackUnit` → 0 (SDK CiscoDevNet/intersight-python, `compute_physical_summary_all_of.py` : « This feild will either be RackUnit or Blade »). Seules ces deux valeurs ont été observées sur l'appliance.
  - **Repli** : si `SourceObjectType` est absent ou a une autre valeur (une autre installation peut ne pas le renvoyer), l'ancienne règle s'applique.
  - Le mode Zabbix 7.0 (par défaut) n'est pas concerné : tous les serveurs y sont découverts. Test : `tests/blade_chassis_matching.test.js`.
- **Correctif : télémétrie rattachée par `host.id` (le `Moid` de l'équipement), avec un repli sur le nom.** Avant, la télémétrie était rattachée par classe (`host.type`) et nom (`host.name`). Or Cisco précise que « the host name is not guaranteed to be unique and may change over time », alors que `host.id` est « a globally unique host ID », le chemin API de la ressource (doc Cisco DevNet, « Host Power and Status »). Deux équipements d'une même classe portant le même nom recevaient donc la même télémétrie mélangée (puissance, températures, PSU, ports). Aucun doublon n'existe sur l'appliance de test : c'est une protection pour les autres installations.
  - **Collecteur** : toutes les requêtes sont aussi groupées par `host.id` (attribut documenté pour les 13 instruments du catalogue). Chaque ligne est rattachée à l'équipement dont le `Moid` est le dernier segment de `host.id` (forme `/api/v1/<espace>/<classe>/<id>`). Vérifié sur l'appliance pour `hw.host` et `hw.power_supply` : ce segment est le `Moid` des lames, racks, châssis et FI, et chaque `host.id` correspond à un seul nom et un seul type. Non vérifié pour les autres instruments (`hw.network`, `hw.temperature`…).
  - **Repli** : une autre installation peut ne pas renvoyer `host.id`. Une ligne sans `host.id` (absent ou vide) est rattachée par classe et nom, ou par nom seul si `host.type` est inconnu, d'après l'inventaire lu juste avant. Un équipement reçoit ainsi toutes ses lignes, même si un instrument renvoie `host.id` et un autre non.
  - **Limite du repli** : si un nom est porté par plusieurs équipements (de la même classe, ou de n'importe quelle classe quand `host.type` est inconnu), ses lignes sans `host.id` sont ignorées. Ces homonymes ne reçoivent pas cette télémétrie, plutôt que des valeurs mélangées. Une ligne dont le `host.id` ne correspond à aucun équipement de l'inventaire n'est attribuée à personne.
  - **Robustesse** : la table indexée par `Moid` n'a pas de prototype (`Object.create(null)`). Un dernier segment de `host.id` comme `__proto__` ou `constructor`, lu dans la réponse HTTP, ne peut donc plus désigner une propriété héritée ni écrire la télémétrie dans `Object.prototype`, d'où tous les objets l'auraient héritée (revue Copilot de la PR #22).
  - Aucun changement de clé d'item : rien à cocher à la réimportation. Test : `tests/telemetry_match_by_host_id.test.js`.
- **Correctif : une requête de télémétrie en échec ne désactive plus les PSU et les ports.** Quand la requête `hw.power_supply` ou `hw.network` échouait, le collecteur envoyait `psus = []` ou `ports = []` pour chaque équipement, et les règles « PSU discovery » et « Network port discovery » remplaçaient de toute façon une liste absente par `[]` (`CUSTOM_VALUE`). Toutes les PSU ou tous les ports de tous les équipements étaient alors déclarés perdus : désactivés après `{$INTERSIGHT.LLD.LOST.DISABLE}` (`1h`), supprimés après `{$INTERSIGHT.LLD.LOST.DELETE}` (`7d`). Même défaut que celui corrigé pour les listes d'inventaire (ci-dessous).

Une requête réussie sans ligne pour un équipement donne toujours `[]` (par exemple, une lame n'a pas de PSU).
  - **Template** : sur les règles « PSU discovery » et « Network port discovery » des trois templates d'équipement, une liste absente fait ignorer la valeur (`DISCARD_VALUE`) au lieu de déclarer les composants perdus. Les délais `{$INTERSIGHT.LLD.LOST.*}` restent une seconde protection.
  - Rien à cocher à la réimportation. Test : `tests/telemetry_failure_components.test.js`.
- **Surveillance de la taille du JSON poussé vers `intersight.raw`.** Cet item Text est stocké en base (1 h d'historique), et Zabbix tronque une valeur Text avant de la stocker : 65 536 octets en MySQL, 65 536 caractères en PostgreSQL (doc Zabbix 7.0, « Creating an item », « Text data limits »). `history_text.value` est de type `t_text`, soit `text` en MySQL (`create/src/schema.tmpl` et `create/bin/gen_schema.pl` de Zabbix 7.0), qui contient au plus 65 535 octets (doc MySQL 8.0, « String Data Type Syntax »). Le plus gros JSON mesuré sur une appliance faisait 37 301 caractères (une FI). Aucun changement de stockage pour l'instant.

Trigger WARNING « Intersight: pushed value larger than {$INTERSIGHT.RAW.SIZE.WARN} bytes », avec la nouvelle macro `{$INTERSIGHT.RAW.SIZE.WARN}` = `50000`. Une taille en octets n'est jamais inférieure au nombre de caractères : le même seuil vaut pour MySQL et PostgreSQL. Quand les mesures cessent (push désactivé ou aucun équipement), la valeur manquante est ignorée et le problème se ferme après 20 minutes sans mesure (`nodata`, doc Zabbix 7.0, « History functions »).
  - **Unité `B`** ajoutée aux unités autorisées. Zabbix l'affiche en base 2 : 1 024 B → « 1 KB », 1 536 B → « 1.5 KB » (doc Zabbix 7.0, « Unit symbols », « Item value suffixes »).
